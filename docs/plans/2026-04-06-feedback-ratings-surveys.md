# Полный технический план реализации модуля Feedback & Ratings (MobileBot)

Данный план составлен на основе ТЗ и описывает реализацию по принципу: **«Что делаем — Что нужно — Как делаем»**.

---

## 🏗 1. Модуль опросов клиентов (бухгалтеров)

### [1.1 - 1.3] Создание динамического опросника в 1С
*   **Что делаем:** Реализуем гибкий конструктор анкет, которые клиент проходит прямо в чате 1С с использованием кнопок.
*   **Что нужно:** 
    1. Таблицы БД для хранения шаблонов и вопросов.
    2. Поддержка интерактивных кнопок в протоколе обмена с 1С.
*   **Как делаем:**
    - **БД:** Создаем `survey_templates` (названия) и `survey_questions` (текст, тип: шкала/выбор/текст/список сотрудников).
    - **Инфраструктура:** В таблицу `outbox_onec` добавляем поле `actions` (json), куда бэкенд упаковывает кнопки (например: `[{"text": "5", "value": 5}, ...]`).
    - **Логика:** Бэкенд хранит `active_surveys`, отслеживая, на каком вопросе остановился клиент. При получении сообщения от клиента система проверяет: если это ответ на опрос — сохраняет его и шлет следующий вопрос кнопками.

### [1.4] Тематики опроса (Качество, Семинары, ИИ)
*   **Что делаем:** Реализуем предзаполненные шаблоны под разные нужды бизнеса.
*   **Что нужно:** Набор предустановленных SQL-инсертов для базы данных.
*   **Как делаем:** Создаем системные шаблоны (ID 1-10), которые администратор может активировать одной кнопкой в Web-панели.

### [1.5] Анонимная и неанонимная модели
*   **Что делаем:** Позволяем проводить "чувствительные" опросы без идентификации автора.
*   **Что нужно:** Флаг `is_anonymous` в шаблоне опроса.
*   **Как делаем:** При сохранении ответа (`survey_answers`), если опрос анонимный, мы записываем `client_id = 0`, но сохраняем `region_id` и `org_type` для глобальной аналитики без возможности деанонимизации.

### [1.6 - 1.7] Аналитическая отчетность
*   **Что делаем:** Сводный дашборд для руководителей.
*   **Что нужно:** SQL-запросы с агрегацией и библиотека ECharts для визуализации.
*   **Как делаем:** Считаем долю позитива/негатива, ТОП пожеланий по обучению и "Черный список" сотрудников по жалобам. Группируем по регионам Казахстана.

## 🛠 2. Оценка клиента по завершённым задачам (Сотрудник)

### [2.1] Трансформация чата в форму оценки
*   **Что делаем:** Автоматически меняем интерфейс оператора на анкету при закрытии тикета.
*   **Что нужно:** Стейт-менеджмент в React (WebApp) и Flutter (Mobile).
*   **Как делаем:** При клике на "Завершить", компонент чата `replac'ится` на `EvaluationComponent`. Пока все "галочки" не проставлены, тикет не считается закрытым в системе.

### [2.2 - 2.4] Параметры оценки и Сбор данных
*   **Что делаем:** Сбор объективных факторов взаимодействия (полнота данных, этика, скорость фидбэка).
*   **Что нужно:** Форма с чекбоксами и выбор причин низких оценок.
*   **Как делаем:** Данные упаковываются в JSON и пишутся в таблицу `evaluations` вместе с ID клиента, датами и флагом "Участие ИИ".

### [2.5] Расчет внутреннего рейтинга (Индекс качества)
*   **Что делаем:** Математический расчет лояльности и адекватности клиента.
*   **Что нужно:** Реализация вашей формулы: `40% (оценка) + 20% (полнота) + 20% (отсутствие деблирования) + 20% (соблюдение сроков)`.
*   **Как делаем:** На бэкенде в момент закрытия задачи рассчитываем этот индекс и сохраняем его в агрегированную таблицу рейтинга клиентов.

## 📊 3. Сводная аналитика оценок (Клиент, Сотрудник, ИИ)

### [3.1 - 3.2] Логика «Кто-Кому» и Регистрация
*   **Что делаем:** Создаем прозрачную историю всех взаимодействий и оценок.
*   **Что нужно:** Таблица `evaluations` с полями `rater_type` и `target_type`.
*   **Как делаем:** Регистрируем направления: `клиент -> сотрудник`, `сотрудник -> клиент`, `сотрудник -> ИИ`, `клиент -> ИИ`, `руководитель -> сотрудник`.

### [3.3] Виды рейтингов
*   **Что делаем:** Расчет KPI для каждого звена системы.
*   **Что нужно:** SQL-вьюхи (Views) для быстрого доступа к рейтингам.
*   **Как делаем:** Для ИИ считаем "Полезность рекомендаций" и "Процент ручной правки". Для персонала — "Доля задач без эскалации".

### [3.4 - 3.5] Аналитика для руководителя
*   **Что делаем:** Интерфейс для глубокого анализа качества.
*   **Что нужно:** Таблица взаимных оценок ("Шахматка") и фильтрация по категориям.
*   **Как делаем:** Реализуем фильтры по Региону, Организации и Категории обращения.

## 🔒 4. Безопасность и Контур доступа

### [4.1 - 4.4] Изоляция данных качества
*   **Что делаем:** Запрещаем операторам видеть плохие отзывы о себе в сыром виде.
*   **Что нужно:** Ролевая модель доступа (RBAC).
*   **Как делаем:** В профиле сотрудника выводим только обезличенную статистику (средний индекс) без привязки к клиенту и без текста комментариев. Прямой доступ к API для получения деталей закрыт для роли `operator`.

### [4.5 - 4.6] Проверка прав и Журналирование
*   **Что делаем:** Защита данных на уровне сервера и логирование действий админов.
*   **Что нужно:** Таблица `audit_access_logs`.
*   **Как делаем:** Любой просмотр сотрудником/админом детальной карточки оценки пишется в журнал: "ID пользователя, Дата, Какое обращение просмотрено, Устройство".

### [4.7] Принцип "Защищенного контура"
*   **Что делаем:** Техническое разделение операционного и контрольного контура.
*   **Как делаем:** Данные по оценкам клиентов хранятся в отдельных таблицах, и ни один метод бэкенда для оператора не возвращает эти данные в "сыром" виде.
