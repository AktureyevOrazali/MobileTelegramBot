# Дизайн сводной аналитики оценок для руководителя

## Контекст

Текущая вкладка `Сводная аналитика` в разделе опросов построена вокруг survey-вопросов и выбора одного вопроса. Это не соответствует целевому сценарию для руководителя.

По ТЗ в этом разделе должна быть именно аналитика оценок в разрезе трёх сущностей:

- клиенты;
- сотрудники;
- ИИ.

Дополнительно должен существовать отдельный аналитический блок `Кто кому поставил оценку`, который показывает структуру и полноту обратной связи.

В текущем фронтенде уже существуют отдельные ratings endpoint'ы для этих данных, но текущий UI их не использует как основу `Сводной аналитики`.

## Цель

Переделать вкладку `Сводная аналитика` в руководительский dashboard, который:

- показывает аналитику оценок по сущностям `Сотрудники / Клиенты / ИИ`;
- использует те же карточки, сетки и визуальный язык, что и другие аналитические страницы;
- содержит отдельный блок `Аналитика взаимных оценок` на той же вкладке;
- использует общий фильтр периода из шапки страницы.

## Не входит в задачу

- переделка вкладки `Опросы клиентов`;
- переделка вкладки `Оценка клиентов сотрудниками`;
- смена глобальной навигации приложения;
- создание новой отдельной страницы вне вкладки `Сводная аналитика`;
- обязательное изменение backend API, если данные уже доступны.

## Источники данных

Для верхнего блока `Сводная аналитика оценок` используются ratings endpoint'ы:

- `fetchRatingsSummary`
- `fetchEmployeeRatingsAnalytics`
- `fetchClientRatingsAnalytics`
- `fetchAiRatingsAnalytics`

Для нижнего блока `Аналитика взаимных оценок` используются:

- `fetchMutualRatingMatrix`
- `fetchRatingLedger`

## Принятое решение

### Общая структура вкладки

Вкладка `Сводная аналитика` делится на две крупные зоны:

1. `Сводная аналитика оценок`
2. `Аналитика взаимных оценок`

### Навигация внутри верхней зоны

Верхняя зона использует переключатель сущности:

- `Сотрудники`
- `Клиенты`
- `ИИ`

В каждый момент времени показывается один активный dashboard для выбранной сущности.

Такой подход выбран вместо длинной страницы со всеми секциями подряд, потому что:

- он сохраняет экран плотным и управляемым;
- он ближе к другим аналитическим страницам;
- он уменьшает визуальный шум для руководителя;
- он не превращает вкладку в перегруженный вертикальный отчёт.

### Положение блока взаимных оценок

Блок `Аналитика взаимных оценок` расположен ниже верхней зоны на той же вкладке.

Причина:

- сначала руководитель видит основную оценочную картину по выбранной сущности;
- затем, не покидая страницу, может проверить полноту и структуру обратной связи.

### Фильтр периода

Фильтр периода из шапки применяется ко всей вкладке:

- к верхнему dashboard по выбранной сущности;
- к блоку взаимных оценок;
- к матрице;
- к журналу оценок.

## Визуальная система

Новая `Сводная аналитика` должна визуально совпадать с уже обновлёнными аналитическими страницами.

Требования:

- использовать те же `surveys`-карточки;
- использовать ту же сетку строк `primary / triple / double`;
- сохранить общую стилистику страницы сотрудников и страницы аналитики клиентов;
- не использовать отдельный визуальный язык для руководительской аналитики;
- обеспечивать одинаковую плотность карточек, отступы, радиусы и тени.

## Верхняя зона: Сводная аналитика оценок

### Общая структура

Для каждой сущности используется одинаковый визуальный каркас:

1. первый ряд из двух больших карточек;
2. второй ряд из трёх карточек;
3. третий ряд из двух карточек-таблиц или комбинации таблицы и графика.

Это даёт визуальную согласованность между `Сотрудники / Клиенты / ИИ`.

## Dashboard: Сотрудники

### Первый ряд

#### Карточка `Общая картина по сотрудникам`

Должна содержать:

- среднюю клиентскую оценку;
- количество оценок;
- количество жалоб;
- количество положительных отзывов.

Формат:

- крупное основное значение;
- 3-4 supporting rows;
- короткое пояснение.

#### Карточка `Динамика и влияние ИИ`

Содержит:

- `line chart` по динамике оценок по периодам;
- визуальный блок зависимости оценки от использования ИИ.

Для влияния ИИ допускаются:

- bar chart;
- компактный split-list;
- сравнительные KPI по сценариям использования.

### Второй ряд

Три карточки:

1. `Причины низких оценок`
2. `Топ лучших сотрудников`
3. `Сотрудники с наибольшим количеством низких оценок`

### Третий ряд

Две карточки:

1. `Рейтинг сотрудников`
2. `Сценарии и влияние ИИ` или дополнительная аналитическая карточка по сценариям, если данных хватает

### Данные, которые обязаны быть представлены

- рейтинг сотрудников по качеству обслуживания;
- средняя клиентская оценка;
- динамика оценок по периодам;
- количество жалоб;
- количество положительных отзывов;
- зависимость оценки от использования ИИ;
- топ лучших сотрудников;
- сотрудники с наибольшим количеством низких оценок.

## Dashboard: Клиенты

### Первый ряд

#### Карточка `Общая картина по клиентам`

Должна содержать:

- рейтинг клиентов по качеству взаимодействия;
- количество обращений;
- долю повторных обращений;
- полноту предоставления данных.

#### Карточка `Динамика и качество взаимодействия`

Содержит:

- `line chart` по периодам;
- дополнительную метрику качества взаимодействия или полноты данных.

### Второй ряд

Три карточки:

1. `Причины низких оценок`
2. `Статусы взаимодействия`
3. `Флаги обращений`

### Третий ряд

Две карточки:

1. `Рейтинг клиентов`
2. `Клиенты, требующие дополнительного обучения и поддержки`

### Данные, которые обязаны быть представлены

- рейтинг клиентов по качеству взаимодействия;
- количество обращений;
- доля повторных обращений;
- полнота предоставления данных;
- клиенты, требующие дополнительного обучения;
- клиенты, по которым рекомендуется проведение вебинаров, семинаров или методической поддержки.

## Dashboard: ИИ

### Первый ряд

#### Карточка `Общая картина по ИИ`

Должна содержать:

- общую оценку ИИ;
- частоту использования;
- ошибки ИИ;
- процент ручной корректировки.

#### Карточка `Динамика и сценарии`

Содержит:

- `line chart` по периодам;
- сравнение по сценариям:
  - человек без ИИ;
  - ИИ без участия сотрудника;
  - сотрудник с подсказками ИИ.

### Второй ряд

Три карточки:

1. `Причины низких оценок ИИ`
2. `Полезность ИИ по категориям`
3. `Разделы, требующие проверки`

### Третий ряд

Две карточки:

1. `Сводка по категориям`
2. `Сценарное сравнение`

### Данные, которые обязаны быть представлены

- общая оценка ИИ;
- полезность ИИ по категориям обращений;
- частота использования;
- ошибки ИИ;
- процент ручной корректировки;
- сравнение по трём сценариям.

## Нижняя зона: Аналитика взаимных оценок

### Назначение

Этот блок нужен для контроля полноты и структуры обратной связи.

Он должен отвечать на вопрос:

`кто кого оценил`, `в каком количестве`, `по каким направлениям`, `с какими параметрами и статусом`.

### Структура блока

Блок строится в три уровня.

#### 1. Верхняя карточка `Сводка взаимных оценок`

Показывает:

- общее количество записей;
- количество покрытых типов связей;
- дату обновления;
- breakdown по основным направлениям оценивания.

#### 2. Две карточки в ряд

1. `Матрица кто кого оценил`
2. `Фильтры`

#### 3. Широкая таблица `Журнал оценок`

Ниже матрицы и фильтров располагается широкая таблица подробных записей.

## Матрица взаимных оценок

Матрица должна покрывать связи:

- клиент оценил сотрудника;
- сотрудник оценил клиента;
- сотрудник оценил ИИ;
- клиент оценил ИИ;
- руководитель оценил корректность закрытия кейса.

Визуально это может быть:

- компактная матрица;
- набор карточек-ячеек;
- таблица-матрица с числом записей и средним баллом.

Главное требование:

- структура должна быстро показывать, какие типы оценок реально используются и в каком объёме.

## Фильтры блока взаимных оценок

Фильтры должны быть доступны внутри блока:

- тип оценщика;
- тип оцениваемого объекта;
- период;
- сотрудник;
- клиент;
- категория обращения / section;
- регион;
- организация;
- участие ИИ.

Если период уже задаётся шапкой, локальный фильтр периода внутри блока можно не дублировать визуально.

## Таблица журнала оценок

В карточке оценки / строке журнала должны отображаться:

- номер обращения;
- кто поставил оценку;
- кому поставил оценку;
- дата;
- балл;
- детализация параметров;
- комментарий;
- участвовал ли ИИ;
- итоговый статус обращения.

Дополнительно допустимы:

- категория обращения;
- организация;
- регион;
- сценарий.

## Поведение пустых состояний

Если часть данных недоступна:

- карточки остаются на месте;
- показывается локальный `EmptyState`;
- сетка не схлопывается.

Если полностью отсутствуют ratings-данные:

- верхняя зона и нижняя зона остаются видимыми как контейнеры;
- внутри показываются понятные пустые состояния, а не исчезновение экрана.

## Изменения в кодовой структуре

### Что должно быть убрано из текущей реализации

- зависимость `Сводной аналитики` от `QuestionAnalyticsWorkspace`;
- выбор одного вопроса;
- screen model, ориентированный на `selectedQuestion` как базовую сущность вкладки.

### Что должно быть добавлено

- отдельный ratings dashboard model для вкладки `Сводная аналитика`;
- локальный переключатель сущности `employees / clients / ai`;
- отдельный screen model builder на каждую сущность;
- отдельный блок mutual ratings под основным dashboard;
- фильтры mutual ratings внутри нижнего блока;
- журнал mutual ratings на основе ledger-данных.

### Что должно быть переиспользовано

- общий shell страницы `SurveysPage`;
- существующие карточки и таблицы;
- `EChartsWrapper`;
- текущие форматтеры чисел, процентов и дат;
- текущие CSS-паттерны аналитических страниц.

## Технические риски и ограничения

### Период и backend-контракты

Фильтр периода должен влиять на всю вкладку. Если часть ratings endpoint'ов не принимает даты, это отдельный технический разрыв между ТЗ и API.

В такой ситуации реализация должна:

- сначала проверить, можно ли передать фильтры через существующий клиент;
- если нет, явно зафиксировать это как backend gap;
- не подменять отсутствующие серверные фильтры клиентской имитацией без явного решения.

### Объём данных в ledger

Журнал оценок потенциально широкий и тяжёлый. Поэтому:

- фильтры должны быть размещены до таблицы;
- таблица должна оставаться scrollable;
- при необходимости используется ограниченный список записей с серверным `limit`.

## Критерии готовности

После реализации должно быть верно следующее:

- вкладка `Сводная аналитика` больше не построена вокруг выбора одного вопроса;
- верхний блок использует переключатели `Сотрудники / Клиенты / ИИ`;
- каждая сущность отображается в dashboard-структуре, близкой к другим аналитическим страницам;
- нижний блок `Аналитика взаимных оценок` находится на той же вкладке;
- блок взаимных оценок содержит сводку, матрицу, фильтры и журнал;
- фильтр периода из шапки применяется ко всей вкладке;
- пустые состояния не ломают сетку;
- визуально страница совпадает по стилю с другими analytics screens.
